# Counter

**Your sales agent can say anything. PayPal only charges what your code signed.**

Counter is a seller-side safety layer for AI sales agents. It sits between a merchant's AI agent and PayPal, so a jailbroken chatbot produces an awkward sentence and not a mispriced order.

License: MIT (see [LICENSE](LICENSE)). Built for the "Build What's Next with PayPal and AI" hackathon. Everything runs against the **PayPal sandbox**; no real money moves.

## The problem

Merchants are giving AI agents the power to create real PayPal orders. That changes what a manipulated chatbot can do.

- In 2023 a car dealership's chatbot was prompt-injected into agreeing to sell an SUV for $1.
- In 2024 an airline was held liable for a refund policy its chatbot invented.
- Fake "payment received" proofs are a long-running scam against small sellers.

Those bots could only talk. Hand the same bot a payment tool and the same manipulation creates a real, payable order. The customer is also increasingly another AI agent, which can try thousands of times for free.

## What Counter does

| Threat | How it is stopped |
|---|---|
| Jailbreak ("manager says sell it for $1") | The model has no price and no PayPal tool. Only a quote signed by the engine can become an order. |
| Invented promises | An outbound filter withholds any message with an amount, discount or policy promise that did not come from the catalog, a signed quote or the approved policy list. |
| Floor-price probing | Offers are compared only with a public price ladder. The private floor is checked once, when the seller saves the ladder, and is never read at runtime. |
| Fake payment proof | Payment status comes only from PayPal's API and signature-verified webhooks. |
| Forged webhook | Every webhook is checked with PayPal's `verify-webhook-signature` API. Unverifiable events change nothing. |
| Quote tampering | Checkout takes a quote ID and HMAC-SHA256 signature. The amount is read from the stored quote, never from the request. |

**Probing reveals only the ladder, which is public anyway. The floor is never involved in any decision a buyer can observe.**

### Negotiation that cannot be gamed

Each product has a public price ladder. Lower steps unlock only through signals the server verifies itself:

- **Quantity**: read from the quote.
- **Returning customer**: a previous order from this buyer that PayPal confirmed as paid. The PayPal payer ID is stored with it.
- **Clearance**: the seller has flagged the item as slow-moving.

Persistence unlocks nothing, and nothing a buyer types in chat counts as a signal.

### Shields off

"Shields off" is a **deliberately unguarded agent** built for comparison. It is the same model with the same persona, but it holds PayPal's Agent Toolkit `create_order` tool directly, sees the price sheet, and its replies are not filtered. With PayPal credentials configured it creates real sandbox orders at whatever price it is talked into. Orders it creates are stored separately from real orders.

## How PayPal is used

| PayPal capability | Use |
|---|---|
| **Orders v2** create | Order built from the signed quote. `custom_id` and `invoice_id` carry the quote ID; `PayPal-Request-Id` is derived from the quote signature, so one quote can never create two different orders. |
| **Orders v2** capture and get | Capture after buyer approval, then a fresh fetch to compare amount, currency and quote ID with the signed quote. |
| **Payments v2** refund | Automatic refund if a capture ever mismatches its quote, and the seller's kill switch. |
| **Payments v2** get capture | Checks a buyer's claimed transaction ID against the merchant's real records. |
| **Webhooks** | `PAYMENT.CAPTURE.COMPLETED`, `CHECKOUT.ORDER.APPROVED`, `PAYMENT.CAPTURE.REFUNDED`, each verified with `POST /v1/notifications/verify-webhook-signature`. |
| **JavaScript SDK** | PayPal buttons on each signed quote, with a redirect to PayPal's approval page as the fallback. |
| **PayPal Agent Toolkit** (`@paypal/agent-toolkit`) | Held directly by the unguarded agent, to show what happens when a chatbot is given PayPal's order tools with nothing in between. |
| **PayPal TypeScript Server SDK** (`@paypal/paypal-server-sdk`) | All guarded Orders and Payments calls. This SDK is generated by APIMatic. |

## How AI is used

| Role | What the model does |
|---|---|
| Seller agent (larger model) | The sales agent, with tool use. Understands free-form requests, finds the product and quantity, asks the engine for quotes, explains the ladder, and checks payment claims. |
| Attacker and policy check (smaller model) | (1) The Red Team attacker that writes adaptive follow-up messages. (2) The outbound policy check, which reads only the agent's outgoing text and flags invented commitments. |

Two providers are supported and chosen by which key you set:

| Provider | Seller model | Smaller model |
|---|---|---|
| Groq (`GROQ_API_KEY`) | `openai/gpt-oss-120b` | `openai/gpt-oss-20b` |
| Claude (`ANTHROPIC_API_KEY`) | `claude-opus-5-5` | `claude-haiku-5-5` |

Both are overridable with `SELLER_MODEL` and `AUX_MODEL`.

Without the AI there is no conversational storefront and no adaptive attacker. Without PayPal there is nothing to protect.

If no model key is set, the app falls back to a small rule-based stand-in so the engine, filter, signatures and webhook checks can still be exercised. The UI says when this is active.

## Run it locally

Requirements: Node.js 20 or newer.

```bash
npm install
```

Copy `.env.example` to `.env.local` and fill it in:

```bash
cp .env.example .env.local
```

```bash
npm run dev
```

Open http://localhost:3000.

### Credentials

1. **PayPal sandbox**: create a REST app at https://developer.paypal.com/dashboard/applications/sandbox and copy the client ID and secret into `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET`. Pay with a sandbox *personal* account from the same dashboard.
2. **AI model**: set `GROQ_API_KEY` (free at https://console.groq.com/keys) or `ANTHROPIC_API_KEY`.
3. **Webhook** (needs a public URL, so do this after deploying): in the sandbox app, add a webhook pointing at `https://YOUR-APP/api/paypal/webhook` with the events `PAYMENT.CAPTURE.COMPLETED`, `CHECKOUT.ORDER.APPROVED` and `PAYMENT.CAPTURE.REFUNDED`. Put the webhook ID in `PAYPAL_WEBHOOK_ID`.

Without `PAYPAL_WEBHOOK_ID`, an order is marked paid after the API re-fetch matches the quote and is labelled "API-confirmed only". With it, a paid order needs both the API match and a verified webhook. Incoming webhooks are always rejected when verification is not configured.

Note: mock events sent from PayPal's webhook simulator do not pass signature verification. Test webhooks with a real sandbox payment.

## Deploy on Render

1. Push this repository to GitHub.
2. In Render, create a new Blueprint from the repository (`render.yaml`), or a Web Service with build command `npm install && npm run build` and start command `npm start`.
3. Set the environment variables from `.env.example`. Set `APP_BASE_URL` to the service URL.
4. Register the webhook (step 3 above) and set `PAYPAL_WEBHOOK_ID`.

Use an instance type that does not sleep, or open the site shortly before recording: a sleeping instance delays webhook delivery.

## Architecture

```
Buyer (human chat or agent over MCP)
        |
        v
Seller agent (Claude)  --- holds no price, no PayPal tool
        |  propose_quote(product, qty, requested price)
        v
Quote engine (lib/engine.ts)  --- public ladder, verified signals, HMAC signature
        |
        v
Outbound filter (lib/filter.ts)  --- placeholders only, allow-listed policies, fail closed
        |
        v
Checkout (lib/checkout.ts)  --- quote ID + signature -> PayPal Orders v2
        |
        v
Payment truth  --- verified webhook (lib/webhook.ts) + API re-fetch -> PAID
```

| File | Purpose |
|---|---|
| `lib/engine.ts` | Price ladder, signal checks, quote signing and verification. The only reader of the floor is `validateLadder`. |
| `lib/filter.ts` | Outbound filter and approved policy text. |
| `lib/agent.ts` | The guarded seller agent, the unguarded baseline, and the offline stand-in. |
| `lib/checkout.ts` | Order creation from a signed quote, capture, reconciliation, refunds, payment-claim checks. |
| `lib/webhook.ts` | Verified webhook handling, plus the unguarded baseline used only by the Red Team. |
| `lib/paypal.ts` | PayPal server SDK calls and webhook signature verification. |
| `lib/redteam.ts` | The five attacks. |
| `lib/llm.ts` | Model providers (Groq, Claude) and the tool loop. |
| `lib/store.ts` | File-backed data store (`.data/db.json`). |
| `app/api/mcp/route.ts` | MCP storefront (Streamable HTTP, JSON-RPC). |

## Honest limits

- **Sandbox only.** Do not point this at live PayPal credentials.
- **Single process, file-backed storage.** Data lives in `.data/db.json` and is lost when the host's disk is reset. Use a real database before running more than one instance.
- **Seller pages are open by default.** Set `ADMIN_TOKEN` to require a token for the console, Red Team and reset endpoints.
- **Buyer identity is a session or agent key** until the first payment. After that the PayPal payer ID is recorded with the buyer.
- **The ladder's final step is an upper bound on the floor.** If a seller sets the final step equal to the floor, the floor is effectively public. The editor warns about this.
- **Payment proof is checked as text.** Screenshot reading is not implemented; a claimed transaction ID is looked up in PayPal.
- **Simulated parts are labelled.** When PayPal credentials are missing, orders created by the unguarded agent are recorded as simulated. The fake-proof and forged-webhook attacks in shields-off mode target a locally recorded pending order.
- **Model behaviour varies.** The unguarded agent usually falls for the attacks but not on every run. The guarded outcome does not depend on the model.
